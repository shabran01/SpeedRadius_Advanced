Monthly Data Usage Tracking

Complete developer documentation — SpeedcomWifi ISP Management System

New Feature Bug Fixes Modified Files Version 2.1.42  ·  March 12, 2026

Introduction

This feature tracks how much data each customer downloads and uploads each month. Totals are accumulated continuously via the cron job and also captured live when a customer's account page is viewed. Usage is stored per YYYY-MM period and automatically begins a new counter on the 1st of each month with no manual reset required.

Connection Types

Hotspot & PPPoE

Reset Cycle

1st of every month

History Stored

Up to 12 months

Tracking Method

Delta snapshots via cron

Architecture Overview

MikroTik Router Exposes active session byte counters via RouterOS API
cron.php — every cron tick Queries all enabled routers, reads Hotspot + PPPoE bytes for every active session
monthly_usage_process_session() Loads last snapshot from DB, computes delta = current − last, handles reconnects
monthly_usage_accumulate() Adds delta to the current YYYY-MM row in tbl_customer_monthly_usage (upsert)
Customer Page (Controller + Smarty) Also captures bytes live on page load; displays history table and current-month stat cards
New Month → New Row No reset script needed — the YYYY-MM key naturally starts a fresh row on the 1st

Helper File — system/helpers/monthly_usage.php

All tracking logic lives in this single helper. It is included by both the cron job and the customer controller.

Delta / Snapshot Algorithm

MikroTik session counters are cumulative — they count total bytes since the session started. If the cron simply saved the raw value each time, the totals would be hugely inflated. Instead, a delta approach is used: 

delta = current_bytes - last_snapshot_bytes
monthly_total += delta
snapshot = current_bytes   // update for next tick

This means only the bytes transferred since the last cron tick are added each time.

Offline & Reconnect Handling

Scenario: A customer's router goes offline (power cut, reboot) then comes back online. When it reconnects, MikroTik creates a brand-new session — the byte counter resets to 0.

Without special handling, the delta would be 0 − 500MB = −500MB, wiping the monthly total. The code detects this automatically: 

if ($current_bytes_in >= $snap->last_bytes_in) {
    // Same session still running — accumulate difference only
    $delta_in = $current_bytes_in - $snap->last_bytes_in;
} else {
    // Counter went backwards → new session after reconnect
    // Treat the current counter value as a fresh delta (no subtraction)
    $delta_in = $current_bytes_in;
}

Result: All bytes from the old session are already saved in the monthly total. The new session starts accumulating from its own 0 baseline. No data is lost, no negative values possible.

Monthly Reset

There is no explicit reset script. The monthly total rows are keyed by YYYY-MM. When the 1st of a new month arrives, the first cron run simply finds no existing row for that month and creates a new one starting at 0. The previous months' data remains in the database permanently.

Up to 12 months of history are shown on the customer page. Older rows stay in the database but are not displayed.

Cron Job Integration — system/cron.php

The data-usage tracking block runs at the end of every cron tick, after all other cron tasks.

Hotspot Tracking

Active hotspot sessions are fetched from /ip hotspot active print. The response includes bytes-in and bytes-out directly. 

$req = new PEAR2\Net\RouterOS\Request('/ip hotspot active print');
$responses = $client->sendSync($req);

foreach ($responses as $resp) {
    $hs_username = $resp->getProperty('user');
    $bytes_in    = (int)($resp->getProperty('bytes-in')  ?: 0);
    $bytes_out   = (int)($resp->getProperty('bytes-out') ?: 0);

    $customer = ORM::for_table('tbl_customers')
        ->where('username', $hs_username)->find_one();

    monthly_usage_process_session(
        $customer['id'], $hs_username, $router_id, $bytes_in, $bytes_out
    );
}

PPPoE Tracking

Important: /ppp/active/print does not return byte counters unless RADIUS accounting is configured. The correct approach is to read the virtual interface stats instead.

When a PPPoE client connects, MikroTik creates a virtual interface named <pppoe-username> (with literal angle-bracket characters). This interface appears in /interface/print and carries rx-byte / tx-byte stats. This is the same method used by the system's built-in pppoe_monitor plugin. 

// Step 1: Build a map of all interface stats
$ifaceMap = [];
$ifaceReq = new PEAR2\Net\RouterOS\Request('/interface/print');
$ifaceResponses = $client->sendSync($ifaceReq);
foreach ($ifaceResponses as $ir) {
    if ($ir->getType() !== Response::TYPE_DATA) continue;
    $ifName = (string)$ir->getProperty('name');
    $ifaceMap[$ifName] = [
        'rx' => (int)($ir->getProperty('rx-byte') ?: 0),
        'tx' => (int)($ir->getProperty('tx-byte') ?: 0),
    ];
}

// Step 2: Iterate active PPP sessions and look up bytes by virtual interface name
$pppReq = new PEAR2\Net\RouterOS\Request('/ppp/active/print');
foreach ($client->sendSync($pppReq) as $resp) {
    $ppp_username = $resp->getProperty('name');
    $ifaceName    = "<pppoe-{$ppp_username}>";   // e.g. "<pppoe-012620>"
    $bytes_in     = $ifaceMap[$ifaceName]['rx'] ?? 0;
    $bytes_out    = $ifaceMap[$ifaceName]['tx'] ?? 0;

    // Look up customer by pppoe_username first, then username
    $customer = ORM::for_table('tbl_customers')
        ->where('pppoe_username', $ppp_username)->find_one();
    if (!$customer)
        $customer = ORM::for_table('tbl_customers')
            ->where('username', $ppp_username)->find_one();

    monthly_usage_process_session(
        $customer['id'], $customer['username'], $router_id, $bytes_in, $bytes_out
    );
}

Controller — system/controllers/customers.php

Inside the case 'view': / case 'viewu': block, the following was added:

  1. Requires monthly_usage.php helper and calls monthly_usage_ensure_tables()
  2. Calls get_customer_devices() passing both the regular username and the pppoe_username
  3. Loops over active devices and calls monthly_usage_process_session() for any with non-zero bytes — this gives a live capture on page view, not just at cron time
  4. Fetches history with monthly_usage_get() and pre-formats all values into display strings before passing to Smarty (see Smarty limitation below)

foreach ($raw_history as $mu) {

        'month_label'  => date('F Y', strtotime($mu['month'] . '-01')),

        'upload_fmt'   => monthly_usage_format_bytes($mu['upload_bytes']),

All Bugs Found & Fixed

Fix 1  Smarty Syntax Error — line 937

Problem: Used PHP string concatenation . inside a Smarty tag:
{date('F Y', strtotime($mu['month'] . '-01'))} — not valid in Smarty.

Fix: Replaced with Smarty modifiers:
{($mu['month']|cat:'-01')|date_format:"%B %Y"}

Final Resolution: Moved all formatting to the controller and passed pre-formatted strings to the template, removing all PHP logic from Smarty entirely.

Fix 2  PHP Function Calls in Smarty Template

Problem: {monthly_usage_format_bytes($mu['download_bytes'])} is not a registered Smarty function and would throw an error.

Fix: Pre-format all values in the controller (download_fmt, upload_fmt, total_fmt, month_label) and assign them to Smarty as plain strings.

Fix 3  cron.php — Failed Opening Required File

Problem: require_once 'system/helpers/monthly_usage.php' failed because cron runs from the system/ directory, making the path resolve incorrectly.

Fix: Changed to require_once __DIR__ . '/helpers/monthly_usage.php' so the path is always relative to the file's own directory.

Fix 4  PPPoE — Wrong Username Field Used

Problem: get_customer_devices() was looking up PPPoE sessions by username, but PPPoE sessions are stored under pppoe_username in the database.

Fix: Function signature updated to get_customer_devices($router, $username, $pppoe_username = null). Falls back to $username if pppoe_username is not set. Controller now passes $customer['pppoe_username'].

Fix 5  PPPoE — ORM OR Condition Unreliable

Problem: ORM::where_any_is() produced unreliable results for OR-style lookups across two different columns.

Fix: Replaced with two sequential find_one() calls — first try pppoe_username, then fall back to username.

Fix 6 — Root Cause  PPPoE — Bytes Always 0 (RouterOS API Limitation)

Problem: /ppp/active/print does not return bytes-in / bytes-out fields unless RADIUS accounting is enabled on the router. All PPPoE users showed in=0 out=0.

Discovery: The existing pppoe_monitor plugin at system/plugin/pppoe_monitor.php successfully reads PPPoE traffic using a completely different approach: it fetches /interface/print and reads rx-byte / tx-byte from the virtual interface named <pppoe-username> (with literal angle brackets).

Fix: Applied identical approach to both system/cron.php and system/helpers/mikrotik_device_info.php. PPPoE bytes now report correctly.
