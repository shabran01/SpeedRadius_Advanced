Cron Expiry Fix

Cron Interval
Every 5 minutes

VPS + MikroTik API

🔴 The Problem

When a hotspot customer's package expired, the system was supposed to remove the customer from MikroTik first, then mark them as expired in the database. But the code was doing it in the wrong order — it marked the database first. So when the router connection failed for any reason, the customer stayed active on MikroTik forever, and the system never tried again.

📋 Real World Example

John buys a 1-day hotspot package. It expires at midnight.

❌ What Happened (Before Fix)

⏰ Midnight — John's package expires
⚙️ Cron runs
✏️ Database updated first: John = EXPIRED (this happened BEFORE router removal)
💥 Router connection fails — brief hiccup, reboot, API timeout
🚫 John NOT removed from MikroTik
🔄 Next cron run: looks for WHERE status = 'on' — John is off in DB → skipped forever
🌐 Website: Shows Expired ✅ 📡 MikroTik: John Still Active ❌ 🍿 John: Free internet forever 😱

💡 Simple Explanation — The Security Guard

Think of the cron job as a security guard whose job is to kick out expired customers.

❌ Old (Broken) Way

1. Guard writes in logbook: "John removed" ← writes FIRST
2. Guard goes to the door to physically kick John out
3. Door is jammed (router offline) — John is NOT removed
4. Next shift: guard sees "John removed" in logbook → ignores John
5. John sits inside enjoying free internet forever 😅

✅ New (Fixed) Way

1. Guard goes to the door and physically kicks John out FIRST
2. John is successfully removed from the router
3. Guard NOW writes in logbook: "John removed"
4. If door was jammed → writes NOTHING → tries again next shift
5. Next shift (5 mins later) — tries again until it works ✅

⚡ Why Router Connection Could Fail

🔄 Router rebooting at that exact moment
🌐 Brief network hiccup between VPS and router
🔒 RouterOS API port temporarily busy
📶 Router overloaded with traffic
🔑 Wrong credentials saved in settings
⏱️ Connection timeout (even 1 second is enough)

🔧 The Fix Applied — system/cron.php

❌ Before (Broken Code)

// Set status to off first to prevent repeated attempts if router connection fails
$u->status = 'off';
$u->save();   // ← Database updated BEFORE router removal ❌

// Then try to remove from router...
(new $p['device'])->remove_customer($c, $p);
// If this fails → customer stuck on router forever, never retried

✅ After (Fixed Code)

// Remove from router FIRST
(new $p['device'])->remove_customer($c, $p);

// Only mark as expired AFTER successful router removal ✅
$u->status = 'off';
$u->save();   // ← Database updated AFTER router removal
// If router removal fails → status stays 'on' → cron retries in 5 minutes

🖥️ Your Setup — VPS + 5 Minute Cron

VPS (Your Server)            MikroTik (Your Router)
       │                                │
       │  ←─── Internet / API ─────────→│
       │                                │
  Cron runs here               Router at your location
  every 5 minutes

Your VPS connects to MikroTik remotely over the internet via the RouterOS API. Since cron runs every 5 minutes, the worst case is now: John gets 5–10 extra minutes of internet if the router was briefly offline at the exact moment his package expired. After that, cron retries automatically — no manual action needed ever.

⚠️ Existing Stuck Customers (Already In This State)

If customers were already stuck (expired on website, still active on MikroTik) before this fix was applied, the new code will NOT auto-heal them because their database status is already off and cron skips them.

Option 1 — Manual MikroTik Removal

Go to MikroTik → IP → Hotspot → Users → delete the customer manually

Option 2 — Database Reset

In your database → tbl_user_recharges → find the customer's record
Change status from 'off' back to 'on'
Wait for next cron run (max 5 minutes)
Cron will now properly remove them from router and mark off ✅
